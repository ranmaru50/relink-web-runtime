# RELink Web Runtime

Experimental Web Runtime and proof-of-concept implementation for **RELink (Real Entity Link)** and **AR-XML**.

RELink is an experimental architecture for linking physical-world entities to digital interfaces using existing Web technologies.

This repository implements the smallest browser-based runtime required to validate the core concept.

## Concept

RELink treats Augmented Reality not only as visual information overlaid on the physical world, but more generally as a state in which the **physical world and digital space can interact with and affect each other**.

The initial proof of concept focuses on a simple interaction loop:

```text
Physical Anchor
    ↓
AR-XML URL
    ↓
RELink Web Runtime
    ↓
AR-DOM
    ↓
Human Interface
    ↓
User Event
    ↓
HTTP Request
    ↓
Digital State Change
```

The first implementation intentionally avoids 3D rendering, spatial graphics, dedicated resolver infrastructure, AI integration, and advanced device capabilities.

The goal is to verify that the basic RELink application model can run using ordinary Web infrastructure.

## Current PoC Scope

The initial runtime supports the following flow:

```text
URL / QR Code
    ↓
Download AR-XML over HTTP(S)
    ↓
Parse AR-XML
    ↓
Generate AR-DOM
    ↓
Render Text / Button elements
    ↓
Handle user events
    ↓
Execute HTTP GET / POST actions
    ↓
Update AR-DOM and displayed state
```

### Supported

* AR-XML loading over HTTP(S)
* XML parsing
* Minimal AR-DOM
* Text output
* Button output
* Click events
* HTTP GET actions
* HTTP POST actions
* Updating displayed text after an action
* Browser-based execution
* Chrome-compatible implementation
* Mobile browser operation where supported

### Not Yet Supported

The following features are intentionally outside the first PoC:

* RELink Resolver
* Anchor UUID resolution
* Manifest files
* Cryptographic signatures
* Anchor trust profiles
* NFC
* BLE
* UWB
* GPS and motion sensors
* Custom AR styling language
* External AR JavaScript
* Worker sandbox
* 3D rendering
* WebXR
* MCP
* AI agents
* Robots or drones
* Device attestation
* Advanced authorization

These may be introduced as separate specifications or extensions after the core model has been validated.

## AR-XML

AR-XML is a declarative markup format describing the interface between a physical context and a digital system.

The minimal PoC model consists of three primary concepts:

1. **Outputs**

   * Information or controls presented to the user.

2. **Events**

   * Events generated by user interaction or, in future versions, physical sensors and anchors.

3. **Actions**

   * Operations triggered by events, such as HTTP requests.

Example:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<ar-content version="0.1">

  <outputs>
    <text id="message">
      Container detected
    </text>

    <button id="register">
      Register
    </button>
  </outputs>

  <actions>
    <action
      id="register-action"
      type="http"
      method="POST"
      endpoint="/api/register" />
  </actions>

  <events>
    <event
      on="click"
      target="register"
      action="register-action"
      success-target="message"
      success-text="Registered"
      error-target="message"
      error-text="Registration failed" />
  </events>

</ar-content>
```

## AR-DOM

RELink does not directly use the browser DOM as the internal representation of AR-XML.

AR-XML is parsed into a separate **AR-DOM**.

```text
AR-XML
   ↓
Parser
   ↓
AR-DOM
   ↓
Renderer
   ↓
Browser DOM
```

This separation is intended to:

* keep the runtime independent from a specific rendering implementation;
* provide a future security boundary for AR scripts;
* allow non-browser renderers;
* support headless, agent, robot, or device runtimes in future implementations.

The browser DOM is treated as a rendering target, not as the source of truth.

## Architecture

The initial Web Runtime is divided into several responsibilities.

```text
RELink Web Runtime
│
├─ Resource Loader
│    └─ HTTP fetch
│
├─ AR-XML Parser
│
├─ AR-DOM
│
├─ Event Engine
│
├─ Action Executor
│    └─ HTTP GET / POST
│
└─ HTML Renderer
     ├─ Text
     └─ Button
```

Platform-specific functionality should remain outside the platform-independent core wherever practical.

Future QR, NFC, BLE, sensor, or native-device integrations should be implemented through adapters.

## Design Principles

### Web Native

RELink should reuse existing Web infrastructure wherever possible.

Examples include:

* HTTP / HTTPS
* DNS
* TLS
* CDN
* Web servers
* existing backend frameworks
* REST APIs
* JavaScript
* standard browser APIs

RELink should not introduce a dedicated networking protocol unless existing Web technologies cannot reasonably provide the required functionality.

### Permissionless

The long-term architecture should allow anyone to publish RELink content without requiring registration with a central RELink authority.

A developer should be able to host RELink resources on infrastructure they control.

### Decentralized

A central RELink cloud service must not be required for the protocol to function.

Managed services may exist for convenience, but self-hosting should remain possible.

### Implementation Independent

AR-XML should not depend on a single browser, vendor, cloud service, or runtime implementation.

### Minimal Core

Features should not enter the core specification merely because they may be useful in the future.

Capabilities such as:

* NFC
* BLE
* UWB
* cryptographic anchor trust
* 3D presentation
* MCP
* AI agent support

should be layered on top of a stable minimal core.

## Proof-of-Concept Goal

The first milestone is complete when the following sequence works in a normal Web browser:

```text
1. Load an AR-XML URL.

2. Download the XML using HTTP(S).

3. Parse the document.

4. Create an AR-DOM.

5. Display a text element.

6. Display a button element.

7. Click the button.

8. Execute an HTTP POST request.

9. Receive a successful response.

10. Update the AR-DOM.

11. Display the updated text.
```

A later demonstration may use a QR code as the physical entry point:

```text
QR Code
    ↓
AR-XML URL
    ↓
RELink Web Runtime
    ↓
AR-DOM
    ↓
Button
    ↓
HTTP Backend
```

This is sufficient to demonstrate the initial RELink hypothesis:

> A physical-world entry point can expose a dynamically distributed digital interface using standard Web infrastructure.

## Future Architecture

The long-term RELink architecture may expand beyond human-facing browser interfaces.

```text
Physical Entity
      ↓
RELink Anchor
      ↓
AR-XML
      ↓
RELink Runtime
   ┌──┴─────────────┐
   │                │
 Human           Machine
 Interface        Interface
   │                │
 Browser         AI / Agent
                    │
                    MCP
                    │
              Robot / Drone
```

Future goals include making physical entities:

* addressable;
* discoverable;
* interactable;
* machine-readable;
* securely operable.

These are long-term architectural goals and are not requirements for the current Web Runtime PoC.

## ローカルデモ（実装済み）

このリポジトリには、最小 PoC を実行するデモとローカルバックエンドを含めています。

```powershell
pnpm install
pnpm server
```

別のターミナルで次を実行し、表示された URL をブラウザで開きます。

```powershell
pnpm dev
```

入力欄の初期値 `/sample.arxml` を Load すると、ローカルバックエンドから AR-XML を読み込みます。表示された「入庫する」ボタンを押すと `POST /api/register` を実行し、AR-DOM と画面内のテキストが「入庫しました」に更新されます。

テストとプロダクションビルドはそれぞれ次で実行します。

```powershell
pnpm test
pnpm build
```

実装は `src/core`（Loader / Parser / Runtime）、`src/dom`（AR-DOM）、`src/actions`（HTTP Action）、`src/renderer`（安全な HTML 描画）に分離しています。Action endpoint は同一オリジンのみ許可し、AR-XML のテキストは `textContent` で描画します。

## Security

The initial PoC intentionally supports only a very limited feature set.

AR-XML content must not be treated as trusted code.

The initial runtime should avoid:

* `eval`;
* `new Function`;
* direct HTML injection;
* execution of inline JavaScript from AR-XML;
* passing AR-XML strings directly to `innerHTML`.

Text originating from AR-XML should be rendered using safe text APIs such as `textContent`.

Future scripting support should execute within an isolated runtime and should not expose the host browser environment directly.
